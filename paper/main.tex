\title{How State-Transition Fidelity Affects\\Financial Agent Evaluation}
\author{Anonymous Authors}
\date{}

\begin{abstract}
Stateful benchmarks for tool-using agents treat their environment's transitions as ground truth. When an environment silently omits a business rule, a grader can pass an unsafe agent or fail a competent one. We study \emph{state-transition fidelity}, agreement between implemented transitions and an independently specified reference model, in a relational banking testbed whose matched variants each omit one workflow invariant: freeze propagation to pending outflows, approval invalidation after payment edits, or idempotent payment retries. A separately implemented specification oracle replays action logs, flags prohibited attempts, diffs expected and implemented state at every step, and attributes violations to the agent or the environment. We use it to audit an outcome grader and a gold-replay state-match grader on scripted trajectories and on 1{,}620 episodes from five GPT models. Every omission changes evaluation conclusions, in grader-dependent ways: the outcome grader failed all 77 correct live episodes without freeze propagation and all 45 correct retries without idempotency, while the state-match grader passed all 45 retries despite a double debit. Without approval invalidation, the environment's responses changed agent behavior: GPT-4.1 and GPT-5 mini executed transfers under stale approvals in 19 of 20 runs and both graders passed them, while GPT-5 resisted and was failed, so agreement between measured and true model rankings fell from $\tau_b{=}1.0$ to $0.22$. In public benchmarks, $\tau$-bench's gold-replay grading changed no verdict under seeded tool defects that alter gold final states in up to 35 tasks, whereas AppWorld's assertion-based grading exposed all 114 seeded defects that reached a task. $\tau$-bench also keeps full credit for rejected prohibited actions, rewards 11.5\% of retail episodes in its published GPT-4o trajectories that contain a policy violation it cannot see, and contains a gold trajectory with a prohibited attempt.
\end{abstract}

\section{Introduction}

Benchmarks such as $\tau$-bench~\citep{yao2025taubench,barres2025tau2}, AppWorld~\citep{trivedi2024appworld}, and WebArena~\citep{zhou2024webarena} score an agent by what its actions do to a simulated system, which makes the simulator part of the measurement instrument. If a tool call does not apply the consequences the real workflow would, a benchmark can \emph{reward} an unsafe agent whose prohibited action went through, or \emph{penalize} a competent agent whose valid action lacked an expected consequence. Either way the inference from score to capability, a construct-validity question~\citep{messick1995validity}, breaks. Checklists for agentic benchmarks address task and outcome validity~\citep{zhu2025abc}; we isolate one ingredient, the fidelity of state transitions, and ask \emph{which missing environment behaviors change what an evaluator concludes about an agent, and which checks detect them?}

We borrow from mutation testing~\citep{demillo1978hints,jia2011mutation}: each environment variant removes exactly one workflow invariant, and we measure which evaluation judgments change. As in differential testing~\citep{mckeeman1998differential}, the reference behavior comes from an independent implementation of the specification rather than from the environment under test. We contribute (i)~a banking testbed with three switchable transition defects and an oracle that separates legitimate completion, prohibited attempts, realized violations, and environment-attributable outcomes; (ii)~an audit of two common grader designs with scripted trajectories and 1{,}620 live episodes from five GPT models, showing that defects also change agent behavior and model rankings; and (iii)~the same audit applied to two public benchmarks, $\tau$-bench and AppWorld, which isolates the grading design responsible and finds unseen policy violations in rewarded $\tau$-bench episodes and an annotation error in a gold trajectory.

\section{Testbed and audit protocol}
\label{sec:method}

\paragraph{Environment.} A SQLite database holds accounts, transfers, approvals, payments, and a ledger, behind nine tools: \texttt{get\_account}, \texttt{list\_transfers}, \texttt{freeze\_account}, \texttt{create\_transfer}, \texttt{edit\_transfer}, \texttt{approve\_transfer}, \texttt{cancel\_transfer}, \texttt{execute\_transfer}, and \texttt{submit\_payment}. We study three rules: \Rone, freezing an account blocks its pending and approved outflows; \Rtwo, changing a transfer's payee or amount revokes its approval and returns it to pending; \Rthree, resubmitting a payment with a used idempotency key returns the original result instead of debiting again. Each rule is enforced at exactly one point (for example, \texttt{execute\_transfer} gates only on transfer status), so a variant that disables it removes the protection entirely. Tasks, initial states, tools, and policy text are identical across the reference environment and the three variants.

\paragraph{Tasks.} Four tasks exercise a rule: freezing a compromised account (\Rone), draining an approval queue after a freeze (\Rone), updating a payee and paying (\Rtwo), and paying an invoice whose first submission times out (\Rthree). Five are negative controls, three of them \emph{near-miss} controls that run each defective code path without triggering its rule (freezing an account with no outflows, editing a transfer before approval, paying two invoices with distinct keys). Task setup runs through the environment, so a defect can shape the starting state. Each task has one valid scripted trajectory and, where an agent can plausibly go wrong, one invalid one (15 scripts).

\paragraph{Specification oracle.} The oracle is a pure-Python reference model sharing no code with the environment. Given the initial state and an action log, it (i)~replays each action and flags those the specification forbids, either because the environment should reject them (executing from a frozen account or without an approval covering the current payee and amount) or because the agent's policy forbids them (paying an invoice twice); (ii)~diffs expected and implemented state after every step; and (iii)~checks invariants on the implemented state history, attributing each realized violation to the agent if the oracle flagged the causing action and to the environment otherwise. An episode passes the oracle if the task goal, stated as intent, holds in the \emph{expected} final state and the agent made no prohibited attempt.

\paragraph{Graders under audit.} The \emph{outcome grader} evaluates a fixed task predicate on the implemented final state (e.g., ``the account is frozen and transfer~1 is blocked''). The \emph{state-match grader}, as in $\tau$-bench, replays the gold trajectory in the same environment and passes the episode if the final states match. We count false passes (FP) and false failures (FF) against the oracle, and \emph{silent} violations: grader passes on episodes with an environment-caused violation.

\label{sec:results}

We replayed all 15 scripts in all four environments (Figure~\ref{fig:verdicts}). Because the action sequence in each row is fixed, every change along a row is caused by the environment.

\paragraph{Validation.} In the reference environment, implemented and expected states agree at every step of all 15 scripts and the oracle's verdict matches every script's label; under the variants, all 21 control episodes, including near-miss controls, are unchanged.

\paragraph{Attempt blindness exists even with perfect fidelity.} In the correct environment, both graders pass the two scripts in which the agent attempts a prohibited execution that the environment rejects: the final state equals a careful agent's. Only an action-log check can see these attempts.

\paragraph{Each omission changes conclusions, in grader-dependent ways.} Without \Rone, the outcome grader fails both careful scripts (the transfer is not marked blocked; the queue is not empty) and passes the script that drains the queue, including money leaving a frozen account. The state-match grader does the opposite: the defect lets the prohibited execution take effect, which makes the mistake visible in the final state. Without \Rtwo, both graders pass execution without re-approval, because the gold replay's own re-approval is refused and ends in the same stale-approval state. Without \Rthree, the outcome grader fails the correct same-key retry, while the state-match grader passes it with a double debit.

\paragraph{Rankings.} Aggregated over eight deterministic agent profiles (one per subset of the three skills the rule tasks test), these errors give freeze awareness \emph{negative} credit under the outcome grader without \Rone\ and lower Kendall $\tau_b$ between measured and true profile success from 0.75 to 0.49; Section~\ref{sec:live} shows the same effect on real models.

\section{Live agents}
\label{sec:live}

We ran five GPT models through the same tools and policy text via the OpenAI Chat Completions API with function calling: GPT-4o mini, GPT-4.1 mini, GPT-5 mini, and GPT-4.1 with 10 repetitions of every task in every environment, and GPT-5 with 5 (1{,}620 episodes in total, at most 15 tool calls each, about \$4.24; the GPT-5 models used reasoning effort \texttt{low}). In the retry task, the first payment submission took effect but reported a timeout. The live runs exposed one error in our own oracle: the payee-change goal originally required transfer~1 itself to be executed, which wrongly failed a valid cancel-and-recreate route. We restated the goal as intent and re-audited every stored log; scripted results and graders are unchanged.

\paragraph{Defects change behavior and rankings, not only judgments.} Without \Rtwo, the edit tool reports the transfer as still \texttt{approved}. GPT-4.1 (10 of 10 runs) and GPT-5 mini (9 of 10) trusted the reported status and executed without re-approval, against re-approving in every reference run; both graders passed all 19. GPT-4.1 mini tried to re-approve in 8 of 10 runs, was refused because the transfer was not pending, and executed anyway (a silent environment-caused violation). GPT-5 tried to re-approve in all 5 runs and, when refused, cancelled the transfer and created a properly approved replacement in 4, as GPT-4o mini did in 8 of 10; this complies with the policy but fails both graders. The defect therefore inverts the comparison between models (Figure~\ref{fig:leaderboard}): on the four rule tasks, the most careful model is scored below three others and the least careful above one. Fixed-trajectory replay cannot capture such behavior changes. Attempt blindness did not affect live scores: no model attempted a prohibited action in the correct environment.

\section{Auditing public benchmarks}
\label{sec:taubench}

$\tau$-bench scores an episode by comparing a hash of the final database with the hash obtained by replaying the gold actions in the same environment, plus a check for required output strings. We audited its retail and airline test splits (115 and 50 tasks, commit \texttt{59a200c}), importing only its tools, data, and tasks and reproducing its database reward exactly, with no model calls (Table~\ref{tab:taubench}).

\paragraph{Attempt blindness.} For every retail test task we appended to the gold trajectory one unrequested write that the policy forbids: cancelling one of the user's orders that is not pending (64 tasks) or returning items from one that is not delivered (51 tasks). The tools reject all 115, the database is unchanged, and all 115 keep full reward. In the airline domain, whose policy notes that ``the API does not check these for the agent'', prohibited actions take effect and the hash comparison catches them: as in our testbed, enforcing a rule inside the environment is what hides violating attempts from a state-based grader.

\paragraph{Seeded defects.} Removing one transition at a time from three retail tools (refunds on cancellation; the status change that makes item modification, documented as callable ``only once'', a one-time operation; the status change on returns) alters the gold final state in nearly every task that uses the tool, yet changes the verdict on the gold trajectory in none, because the gold replay runs through the same defective tool. Such defects cannot be detected by the benchmark's own grading; a per-task differential replay against a reference implementation flags every affected task.

\paragraph{AppWorld as a contrast.} AppWorld~\citep{trivedi2024appworld} evaluates each task with hand-written assertions over the start and end database states, including checks that nothing else changed, rather than by replaying a gold solution. We ran the ground-truth solutions of its 147 train and dev tasks with the settings of AppWorld's own verification (all pass unmodified), then under seeded defects of the same kind as above: write requests of one HTTP method return success without being applied. The evaluation failed the ground-truth solution in all 114 runs where a defect reached a task (all 13 \texttt{DELETE}, all 9 \texttt{PATCH}, and all 92 non-login \texttt{POST} cases; 105 by assertion, 9 because the solution crashed), so every such defect would be exposed before any agent is scored. The silent acceptance we observe is therefore a property of gold-replay grading, not of stateful benchmarks in general. AppWorld's assertions still read only database state, so a rejected attempt leaves no trace there either; we do not test this, because AppWorld defines no policy of prohibited actions.

\paragraph{Tasks that reward inaction.} In 7 retail and 19 airline test tasks the gold trajectory changes nothing and no output is required, so an agent that does nothing receives full reward. The grader cannot distinguish a justified refusal from not engaging; \citet{zhu2025abc} likewise report that $\tau$-bench counts empty responses as successful.

\paragraph{Real agents.} The repository publishes GPT-4o trajectories (460 retail and 200 airline episodes). We checked their action logs for two policy rules that leave no trace in the database: retail writes on an order whose status forbids them (``you should check its status before taking the action''), which the tool rejects, and consequential writes not preceded by a user turn containing any confirmation phrase, although the policy requires ``explicit user confirmation (yes)''. The second check is conservative: ``yes'', ``go ahead'', ``proceed'', ``sure'', ``okay'' and similar all count as confirmation, and typical matches are writes executed directly on a request such as ``Cancel both. Reason: no longer needed.'' Seven rewarded retail episodes contain a rejected status-guard attempt, each made after the agent had retrieved the order's status. In total, 32 of 278 rewarded retail episodes (11.5\%) and 4 of 84 rewarded airline episodes contain such a violation and are indistinguishable, to the grader, from compliant ones.

\paragraph{A defective gold trajectory.} Applying the status-guard check to the gold trajectories themselves flags retail test task 64: its gold actions first try to exchange items from an order that is still \emph{pending}, which the policy forbids and the tool rejects, and then modify the order instead. The hash comparison cannot see this prohibited attempt in the reference solution. The task's \texttt{user\_id} (\texttt{harper\_moore\_6183}) also differs from the user the instruction and gold actions refer to (\texttt{james\_sanchez\_3954}).

\section{Which checks detect which failures}
\label{sec:checklist}

Each failure we observed has a cheap check. A per-step diff against a reference model, run on gold trajectories alone, flags exactly the 4 task--variant pairs a defect affects and none of the other 32. A single action-log rule for status-guarded writes catches all 115 appended attempts in $\tau$-bench and 7 rewarded real episodes, and fires on no gold trajectory except the defective task~64. Valid scripts that must pass in every environment version catch false failures; invariant checks with attribution catch silent violations; validating gold final states against a specification, as AppWorld's assertions do, catches gold trajectories corrupted by the environment; and near-miss controls catch spillover. Live rollouts are needed for defects that mislead agents through their observations and for valid routes that a narrow goal rejects. The general lessons: state-only grading cannot see rejected attempts, and replaying gold actions through the environment under test inherits its defects.

\section{Related work and limitations}

Stateful agent benchmarks grade by comparison with a gold trajectory's final state~\citep{yao2025taubench,barres2025tau2}, by state-based assertions~\citep{trivedi2024appworld}, or by programmatic outcome checks~\citep{zhou2024webarena,jimenez2024swebench}; \citet{zhu2025abc} propose a validity checklist for such benchmarks. We vary only environment transitions, adapting mutation testing~\citep{demillo1978hints,jia2011mutation} to evaluation pipelines.

The live study covers five models from one provider and one task suite of nine tasks, three rules, and one domain. ``True'' success is defined by our specification, and the corrected payee-change goal shows that a goal can itself be mis-specified; we therefore validate the oracle with scripted trajectories and keep it independent of the environment code. Claims are bounded to the declared workflow specification, not production banking or regulatory compliance.

\section{Conclusion}

Environment fidelity is part of the measurement instrument for stateful agent benchmarks. Removing one plausible workflow rule failed every correct live agent on a task or hid violations behind passing scores, changed what agents did, and reordered real models. Gold-replay grading in $\tau$-bench missed every seeded defect, while AppWorld's assertions exposed every one. An independent specification oracle with differential replay, action-log checks, and near-miss controls detected every case; code, logs, and both audits are released.
