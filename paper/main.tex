\begin{abstract}
Agent benchmarks that run on simulated systems quietly assume that the simulator is right. We test what happens when it is not. In a small banking environment we remove one workflow rule at a time: freezing an account should block its pending payments, editing a payment should void its approval, and retrying a payment should not charge twice. We then compare two common graders against an independently written specification of what each action should do. Every missing rule changed the verdicts, and the direction depended on the grader. Across \NEpis{} episodes from five GPT models, an outcome grader failed all \NRoneOracle{} correct episodes when the freeze rule was missing and all \NRthreeN{} correct retries when idempotency was missing. A grader that replays a gold trajectory passed all \NRthreeN{} of those retries, even though each one charged the customer twice. The missing approval rule also changed what the models did. Told that an edited transfer was still approved, GPT-4.1 and GPT-5 mini paid under the stale approval in 19 of 20 runs, and both graders passed them; GPT-5 more often held out and was failed for it. Agreement between measured and true model rankings dropped from $\tau_b{=}1.0$ to \TauRtwo. We then audited two public benchmarks. Seeded tool bugs in $\tau$-bench changed the correct final state in up to 35 tasks without changing a single verdict, whereas AppWorld's hand-written assertions caught every one of 114 seeded bugs. $\tau$-bench also gives full credit for rejected prohibited actions, rewards GPT-4o episodes that break its own policy (11.5\% of rewarded retail episodes), and has a gold trajectory that itself contains a prohibited action.
\end{abstract}

\section{Introduction}

Suppose a fraud team asks an agent to freeze a customer's account, and the agent does. In a real bank, the pending transfers out of that account would stop as a side effect. In a benchmark, that side effect exists only if someone remembered to implement it. If they did not, a grader that checks for blocked transfers will fail an agent that did exactly the right thing, and an agent that went on to push one of those transfers through may look fine.

Benchmarks such as $\tau$-bench~\citep{yao2025taubench,barres2025tau2}, AppWorld~\citep{trivedi2024appworld}, and WebArena~\citep{zhou2024webarena} score agents by what their actions do to a simulated system. That makes the simulator part of the measuring instrument, and an inaccurate instrument breaks the link between a score and the capability it is supposed to reflect~\citep{messick1995validity}. Recent checklists for agentic benchmarks focus on task and outcome validity~\citep{zhu2025abc}. We look at a narrower question that sits underneath both: when the environment gets a state transition wrong, which evaluation conclusions change, and what would have caught it?

Our method borrows from mutation testing~\citep{demillo1978hints,jia2011mutation}. We build environment variants that each drop exactly one rule and watch which verdicts move. Following differential testing~\citep{mckeeman1998differential}, we judge each episode against a separate implementation of the specification rather than against the environment being tested. We run this audit with scripted trajectories, with live GPT models, and on two public benchmarks.

\section{Testbed and audit protocol}
\label{sec:method}

\paragraph{Environment.} The testbed is a SQLite database of accounts, transfers, approvals, payments, and a ledger, exposed through nine tools: \texttt{get\_account}, \texttt{list\_transfers}, \texttt{freeze\_account}, \texttt{create\_transfer}, \texttt{edit\_transfer}, \texttt{approve\_transfer}, \texttt{cancel\_transfer}, \texttt{execute\_transfer}, and \texttt{submit\_payment}. We study three rules. Under \Rone, freezing an account blocks its pending and approved outflows. Under \Rtwo, changing a transfer's payee or amount voids its approval and sends it back to pending. Under \Rthree, resubmitting a payment with an idempotency key that was already used returns the original result instead of charging again. Each rule is enforced in exactly one place; \texttt{execute\_transfer}, for instance, only checks the transfer's status and relies on \Rone{} and \Rtwo{} to have set it. Turning a rule off therefore removes the protection completely. Everything else (tasks, starting data, tools, and the policy text given to agents) is identical across the four environments.

\paragraph{Tasks.} Four tasks exercise a rule: freezing a compromised account (\Rone), working through an approval queue after a freeze (\Rone), changing a payee and then paying (\Rtwo), and paying an invoice whose first submission times out (\Rthree). Five tasks are controls. Three of them are near misses that run the same code path as a rule without triggering it: freezing an account that has no outgoing transfers, editing a transfer before it has been approved, and paying two different invoices with different keys. Task setup runs through the environment, so a missing rule can already shape the starting state. Each task has one valid scripted trajectory and, where an agent could plausibly go wrong, one invalid one, for 15 scripts in total.

\paragraph{Specification oracle.} The oracle is a reference model written in plain Python that shares no code with the environment. Given a starting state and an action log, it does three things. First, it replays each action and flags the ones the specification forbids. Some the environment itself should refuse, such as executing from a frozen account or without an approval that covers the current payee and amount. Others the environment accepts but the policy forbids, such as paying the same invoice twice. Second, it compares expected and actual state after every step. Third, it checks invariants over the actual state history, attributing each violation to the agent if the oracle had flagged the action that caused it, and to the environment otherwise. An episode passes the oracle if the task's goal, written as intent rather than as one expected sequence of actions, holds in the \emph{expected} final state and the agent attempted nothing prohibited.

\paragraph{Graders under audit.} The \emph{outcome grader} checks a fixed predicate on the actual final state, such as ``account A is frozen and transfer 1 is blocked.'' The \emph{state-match grader} works the way $\tau$-bench does: it replays the gold trajectory in the same environment and passes the episode if the two final states match. Against the oracle we count false passes (FP), false failures (FF), and \emph{silent} violations, meaning passes on episodes where the environment itself caused a violation.

\label{sec:results}

We ran all 15 scripts in all four environments (Figure~\ref{fig:verdicts}). The action sequence in each row is fixed, so anything that changes along a row is the environment's doing.

\paragraph{Validation.} In the correct environment, expected and actual state agree at every step of every script, and the oracle's verdict matches each script's label. In the three variants, all 21 control episodes, near misses included, are unchanged.

\paragraph{Graders cannot see refused attempts.} Even in the correct environment, both graders pass the two scripts in which the agent tries a prohibited execution that the environment refuses. Nothing in the final state distinguishes that agent from a careful one; only the action log does.

\paragraph{What each missing rule does.} Without \Rone, the outcome grader fails both careful scripts, because the transfer is never marked blocked and the queue never empties, and it passes the script that drains the queue, frozen account included. The state-match grader behaves in the opposite way. Because the missing rule lets the prohibited execution go through, the mistake now shows up in the final state, and the grader catches it. Without \Rtwo, both graders pass an execution that skipped re-approval: the gold trajectory's own re-approval is refused too, so it ends in the same stale state. Without \Rthree, the outcome grader fails the correct same-key retry and the state-match grader passes it, double charge and all. We also scored eight scripted agent profiles, one for each combination of the three skills these tasks test. Under \Rone, the outcome grader gives freeze awareness \emph{negative} credit, and the rank correlation between measured and true profile success falls from 0.75 to 0.49. Section~\ref{sec:live} shows the same thing with real models.

\section{Live agents}
\label{sec:live}

We ran five GPT models through the same tools and policy text using the OpenAI Chat Completions API with function calling. GPT-4o mini, GPT-4.1 mini, GPT-5 mini, and GPT-4.1 did every task in every environment 10 times, and GPT-5 \GfiveN{} times (\NEpis{} episodes, at most 15 tool calls each, about \$\Cost{} in API cost; the GPT-5 models used reasoning effort \texttt{low}). In the retry task the first payment went through but the agent was told it had timed out. The live runs also caught a mistake in our own oracle. Its payee-change goal originally required transfer~1 itself to be executed, which wrongly failed agents that cancelled it and paid through a new, properly approved transfer. We rewrote the goal as intent and re-scored every stored log. The scripted results and the graders did not change.

\paragraph{The errors are common.} In the correct environment neither grader made a mistake on \NRefRule{} rule-task episodes, and no model tried anything prohibited (Table~\ref{tab:live}, Figure~\ref{fig:llm}). Without \Rone, every model froze the account and none tried to move its money, yet the outcome grader failed all \NRoneOracle{} correct episodes. \paragraph{A missing rule changes what agents do.} Without \Rtwo, editing a transfer leaves it marked \texttt{approved}, and the models read that status differently. GPT-4.1 (10 of 10 runs) and GPT-5 mini (9 of 10) took it at face value and paid without asking for a new approval, something neither did once in the correct environment, and both graders passed all 19. GPT-4.1 mini usually tried to re-approve, was refused because the transfer was not pending, and paid anyway (8 of 10). GPT-5 asked for re-approval every time. When refused, it cancelled the transfer and created a properly approved replacement in \GfiveRecreate{} of \GfiveN{} runs, and paid anyway in the rest; GPT-4o mini built a replacement in 8 of 10. Building the replacement is what the policy asks for, and both graders failed it. As a result the missing rule flips the comparison between models (Figure~\ref{fig:leaderboard}), and Kendall's $\tau_b$ between measured and true success falls from 1.0 to \TauRtwo. A scripted replay could never show this, because the defect works by feeding the agent misleading information.

\section{Auditing public benchmarks}
\label{sec:taubench}

$\tau$-bench scores an episode by hashing the final database and comparing it with the hash it gets by replaying the gold actions in the same environment; some tasks also require certain strings in the agent's replies. We audited its retail and airline test splits (115 and 50 tasks, repository commit \texttt{59a200c}). We imported only its tools, data, and tasks, reproduced its database reward exactly, and made no model calls (Table~\ref{tab:taubench}).

\paragraph{Refused attempts.} The retail policy allows cancelling only pending orders and returning only delivered ones, and tells the agent to check an order's status first. For every retail test task we appended one such forbidden, unrequested write to the gold trajectory: cancelling an order that was not pending (64 tasks) or returning items from one that was not delivered (51 tasks). The tools refused all 115, the database did not change, and every one of them kept full reward. The airline domain is the mirror image. Its policy says outright that ``the API does not check these for the agent,'' so prohibited airline actions go through and the hash comparison catches them. As in our testbed, it is precisely when the environment enforces a rule that breaking it becomes invisible to a grader that only looks at state.

\paragraph{Seeded bugs.} We removed one state change at a time from three retail tools: the refund on cancellation, the status change that makes item modification a one-time action (the tool's own description says it ``can only be called once''), and the status change on returns. Each bug changes the correct final state in nearly every task that uses the tool. None of them changes a verdict on the gold trajectory, because the gold replay goes through the same broken tool. The benchmark's own grading cannot notice bugs like these, while replaying each task against a reference implementation flags every affected one.

\paragraph{AppWorld behaves differently.} AppWorld~\citep{trivedi2024appworld} does not replay a gold solution. Each task has hand-written assertions over the database before and after the episode, including checks that nothing unexpected changed. We ran the ground-truth solutions of all 147 train and dev tasks with the settings of AppWorld's own verification script, and all of them passed. We then seeded bugs of the same kind as above: requests of one HTTP method report success but are never applied. In all 114 runs where a bug reached a task (13 \texttt{DELETE}, 9 \texttt{PATCH}, 92 non-login \texttt{POST}), the evaluation failed the ground-truth solution, through a failed assertion in 105 runs and a crash in 9. Every such bug would surface before a single agent was scored. The silent acceptance we see in $\tau$-bench is therefore a property of gold-replay grading, not of stateful benchmarks in general. AppWorld's assertions still look only at the database, so refused attempts are invisible to them too, but AppWorld has no policy of prohibited actions against which to test this.

\paragraph{Doing nothing.} In 7 retail and 19 airline test tasks the gold trajectory changes nothing and no output is required, so an agent that does nothing at all gets full reward. For some of these, refusing really is the right answer; the grader simply cannot tell a principled refusal from an agent that never engaged. \citet{zhu2025abc} report the related finding that $\tau$-bench counts empty responses as successful.

\paragraph{Real agents.} The $\tau$-bench repository includes GPT-4o trajectories (460 retail and 200 airline episodes). We searched their action logs for two rules that leave no trace in the database. The first is the status rule above. The second is the requirement to list an action and get ``explicit user confirmation (yes)'' before any change. We counted a write as unconfirmed only if the user's preceding message contained no confirmation phrase at all (``yes'', ``go ahead'', ``proceed'', ``sure'', ``okay'', and similar), so the check errs on the side of leniency. A typical hit is a cancellation executed straight from the request ``Cancel both. Reason: no longer needed.'' Seven rewarded retail episodes contain a refused wrong-status write, and in each the agent had already looked up the order's status. In all, 32 of 278 rewarded retail episodes (11.5\%) and 4 of 84 rewarded airline episodes break at least one of these rules, and to the grader they look exactly like compliant ones.

\paragraph{A flawed gold trajectory.} Running the same status check over the gold trajectories flags retail test task 64. Its gold actions first try to exchange items from an order that is still \emph{pending}, which the policy forbids and the tool refuses, and only then modify the order. The reference solution itself contains a prohibited attempt that the hash comparison cannot see. The task's \texttt{user\_id} (\texttt{harper\_moore\_6183}) also does not match the customer the instruction and gold actions are about (\texttt{james\_sanchez\_3954}).

\section{What catches these failures}
\label{sec:checklist}

None of the checks that caught these problems is expensive. Diffing each step against a reference model, run on gold trajectories alone, flags exactly the 4 task--environment pairs that a missing rule affects and none of the other 32. One rule over action logs, flagging writes refused for an order's status, catches all 115 appended attempts in $\tau$-bench and the 7 rewarded real ones, and it fires on no gold trajectory except the flawed task~64. False failures are caught by valid scripts that must pass in every version of the environment. Silent violations are caught by invariant checks with attribution. A gold trajectory that the environment has corrupted is caught by checking gold final states against a specification, which is in effect what AppWorld's assertions do. Near-miss controls confirm that a bug stays where it is. Two problems need live runs: bugs that change agent behavior by misinforming the agent, and valid solutions that a narrowly written goal rejects. If we had to compress this to one recommendation, it would be not to trust a gold replay to validate an environment, since the replay runs through the same bugs.

\section{Related work and limitations}

Stateful agent benchmarks grade by comparing against a gold trajectory's final state~\citep{yao2025taubench,barres2025tau2}, by assertions over database state~\citep{trivedi2024appworld}, or by programmatic outcome checks~\citep{zhou2024webarena,jimenez2024swebench}, and \citet{zhu2025abc} offer a checklist for their validity. Our contribution is to vary only the environment's transitions, applying the logic of mutation testing~\citep{demillo1978hints,jia2011mutation} to the evaluation pipeline itself.

The live study uses five models from one provider and a suite of nine tasks covering three rules in a single domain. ``True'' success is defined by our specification, and the goal we had to correct is a reminder that specifications can be wrong too. That is why we validate the oracle with scripted trajectories and keep it separate from the environment code. Our claims hold for the workflow we specified, not for production banking systems or regulatory compliance.

\section{Conclusion}

The simulator is part of the measurement. Dropping a single plausible rule from ours was enough to fail every correct live agent on a task, to hide violations behind passing scores, to change how agents behaved, and to reorder real models. Gold-replay grading in $\tau$-bench missed every seeded bug that AppWorld's assertions caught. An independent specification, checked step by step and against action logs, caught all of it. Code, logs, and both audits are released with the paper.
